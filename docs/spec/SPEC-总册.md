## 一、总则

### 1. 「完成」的定义（全季改版，2026-11-18 起生效）

一项功能**在发布 staging 包内实际验到**才算完成：包内启动、包内操作、
包内出结果。源码里有、单元测试过、开发机上跑过——都不算完成。每阶段
验收条文必须单列一条「包内验证」，写明包内验了什么、证据在哪。

### 2. 负面清单（任何面、任何阶段不许违反）

1. **不重建 console dist**：发布正典是 wb 世代 dist；从 apps 源码重建 =
   主题全灭（已有裁决）。前端改动只走主题叠加层 / 后端 / dist 内静态文件
   的定点修订（如 sw.js 追加处理器），不许整包重建。
2. **一个界面不出现两个同功能入口**：同一功能在一个面上只能有一个入口
   （跨面跳转不算重复，本面内重复即违规）。
3. **用户可见面不放内部信息**：登录页与一切用户可见面不许出现原始错误
   码、英文内部串、调试计数、内部路径、内部代号；出错只给人话与下一步。
4. **Keys 不落明文**：Key / 令牌 / 口令不进日志、不进 git、不进任何响应
   与状态接口；只走安全存储与环境变量。
5. **精而简**：新能力默认关，或藏在聊天 / 设置之后；每项新能力必须能用
   一句话在聊天里触发 / 管理，做不到即缺陷。
6. **不改既有用户数据语义**：升级不许让老数据换含义；迁移必须可回读验证。

### 3. 先卡后工

任何用户可见面动工之前，先在本目录补一张规格卡（五件：布局结构、各
状态、断点行为、显示/隐藏清单、用户可见文案清单），验收按卡逐条对。
没有卡的面不许动工；施工中发现卡与实况不符，先改卡（记理由）再施工。

### 4. 规格体检（常设纪律）

每轮大升级收尾做一次规格体检：抽查全部用户可见面逐条对总册与规格卡，
漂移立账（记入当季总报告）。体检通过线 = **零缺口**（见第三节盘点口径：
每项要么有卡、要么有「不立卡」裁决，不许空白）。

## 三、规格盘点与缺口（V4 落地，本节为口径）

对全产品做一次规格盘点，逐项登记，不许留空白项：

- **面**：全部用户可见页面 × 主题（经典 / 未来）× 断点（桌面 / 412 / 390 / 360）；
- **能力**：27 个 Boss 项 + 系统能力（语音 / 同步 / 更新 / 备份 / 推送 / 技能包 / 多 Bot / 路由等）；
- **数据**：账号包 / 知识 / 记忆等每类数据的规格（格式、保留、迁移、恢复）。

每项三选一：① 已有规格 → 注明出处（本册条文号 / 规格卡 / 既有正典文档）；
② 缺口 → 补写规格卡进本目录；③ 不需要规格 → 写明「不立卡」裁决与理由。
盘点表 + 补齐结果进本册附录与当季总报告；收尾体检以零缺口为通过线。
盘点清单可在 V1.5 期间先拉，补写随 V4 落地（避开与 V1.5 的主题文件抢工）。

**预登记裁决**：`apps/console`（os 世代源码树）不是用户可见面（发布包内
不可达，见前端两代对齐审计），**不立卡**；其规格地位 = 冻结，理由与对齐
路径见 V4 的 DOM 契约文档。
