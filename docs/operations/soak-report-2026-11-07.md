**判定依据与结论**

1. **RSS：疑似泄漏（持续增长型）**。全窗首尾 +40.8%，三分区中位数 +21.3%，平均斜率 +32.9 MB/h；只看段内斜率是 40.8 → 56.1 → 73.5 → 91.6 MB/h，**越跑越快**，且每次重启只能压回约 190MB 而新基线在抬高（208.0MB）。2 小时内不会崩，但按任务书口径"单调增长且不回落"成立。造成增长的具体分配来源未在本轮定位（需更长窗口 + `tracemalloc` 分代快照），不把猜测写成结论。
2. **句柄：2 小时全窗因重启复位而显示 -6.6%，但这会低估"不重启"场景**。段内斜率 +160~215/h、mono 0.70~0.83，说明单进程生命周期内持续累积，只有强杀才清零。两天不重启是持续增长风险（~+200/h → 48h 约 +9600，相对 Windows 进程句柄上限不致命，但与 RSS 同向，值得跟踪）。
3. **线程：无泄漏**（启动后稳定 31）。
4. **DB / goals.json：不是"是否泄漏"，而是确定的无回收线性增长**（mono=1.00，零回落）。DB 约 +21.5MB/h，goals.json 约 +2.42MB/h；它们的增长直接对应后文"越用越卡"。
5. **WAL：不回落，但没有加速**。见 6.1。

## 6. 资源上限

### 6.1 WAL 与 checkpoint

- 总 WAL：**7.80 → 14.53MB**，120 分钟内 **0 次下降**（不只是没有 >30% 的整段回落，是任何一次下降都没有）。
- 但拆到单库，各 WAL 稳定在约 4MB（审计 4.18MB、artifacts 4.14MB、execution.journal 4.13MB、会话 2.38MB）≈ SQLite 默认 1000 页自动 checkpoint 窗口。
- 判定：**自动 checkpoint 在工作**——审计库 2 小时内实际新增约 21MB 数据，若 checkpoint 不工作，其 WAL 应累积到 20MB 以上；现在稳定在 4.18MB 即为证据。**但 WAL 文件不会被截断**（未设置 `journal_size_limit`），所以总量在原位占用 ~14.5MB，并在稳态下以 +1MB/h 缓慢爬升（末 10 分钟仅 +0.09MB）。不是无界膨胀，但也不是零增长。

### 6.2 logs 轮转

- 前 85 分钟（我自己的隔离进程）`run/logs/liuhao.log` 从 0.36KB 线性长到 **7.79MB**（+4.8MB/h），未出现 `.1` 备份 —— **本轮的隔离目录没有跑到 10MiB 阈值**（约 2h 会到）。
- 90 分钟后失真：`6a2e361e`（提交时间 01:19:58，工作树更早已落地）把相对日志路径解析到数据目录，而我的隔离 env 只设了 `LIUHAO_INSTANCE_ROOT`，没设 `LIUHAO_LOG_DIR`；第 4 次启动（01:14:54）起文件日志写到了真实 `%LOCALAPPDATA%\LiuHao\data\logs\liuhao.log`。这是我这一侧隔离设置的缺口（不是产品缺陷），也导致 `logs_bytes` 从 90 分钟起冻结在 7.79MB。**需要登记：隔离脚本必须显式设置 `LIUHAO_LOG_DIR`。**
- 关于"日志超过 10MiB / 丢记录"：按**修复前**行为解释——`config/logging.yaml` 每个通道用标准库 `RotatingFileHandler`（10MB × 5 备份），Windows 上多进程同时持有时 rename 失败（共享冲突），该条记录被丢弃且文件继续增长、越过 10MiB。本轮没有复现到 10MiB 轮转节点（原因见上），因此不补造实测；**修复后的多进程安全验证结果由 `6a2e361e` 那一路给出**，我这里只确认本进程链上 0 条 `persist failed` / 0 条 Traceback / 0 条 ERROR（121 条 WARNING 中主要是 JWT 密钥长度提示）。

### 6.3 DB 是否无界膨胀

- 库总量：**1.77 → 44.53MB**，两小时 +42.8MB，斜率稳定 +21.4~21.8MB/h（四个段几乎相同），**单调、零回落**。
- 审计条目从 13,066 → 46,454（每 30 分钟 +约 1.1 万条），审计库 45.8MB。
- 判定：**是线性无界增长**（审计 append-only 设计使然），本轮未看到 retention/vacuum/归档。按此负载外推：一天约 +0.5GB，两天约 +1GB。磁盘上尚可接受，但 `/v1/audit/verify` 的成本随条目数线性上升（见 6.4），所以它与"越用越卡"是同一个问题。

### 6.4 为什么会"越来越卡"（回归证据）

- `/v1/audit/verify`：p50 271 → 2532ms（**9.3 倍**），每 15 分钟窗口的 p50 依次为 271/569/818/1100/1395/1671/2010/2312/2532ms，条目数同步从 1.3 万涨到 4.6 万；斜率 +19ms/min。按线性外推，24h ~28s、48h ~55s/次。
- `POST /v1/goals` p50 284 → 954ms（+5.83ms/min），`/v1/goals/assign` 303 → 957ms（+5.80ms/min），与 `liuhao_goals.json` 从 0.17MB 涨到 4.96MB 同步；写路径是"文件锁 + 读全量 → 合并 → 整文件 `os.replace`"，成本随文件增长。
- 知识库检索基本持平（+0.3ms/min），会话延迟由模型支配，未见随运行时间劣化。
