## 1. 首屏长什么样

### 观察结果

**登录后的第一屏是「总览」仪表盘，不是对话框，也不是功能列表。**

从上到下是四层：

1. **窗口壳**：自定义标题栏 + 左侧窄侧栏 + 右侧主面板；没有全局顶部导航条。
2. **四块 KPI**：今日已省 token、今日花费、消耗速率、上下文占用。数字是等宽字体，实时变化。
3. **Agent 健康卡**：一个分值（如 74）+ 活跃 agent 数 + 问题数 + 可追回金额 + 一键「Fix」。
4. **已接管会话列表**：每个 agent 一行，显示 token 增量、费用、live 状态；行可点击跳转到该 agent 的实时日志。

首屏没有「欢迎使用」「开始创建任务」这类空态主视觉；它默认假设你已经把 agent 接进来了，第一眼回答的是「现在花了多少、省了多少、哪个 agent 有问题」。

首启（登录前）是另一屏：亮色单页，中央一张设备框，框内是主题色选择（一组圆形色板，默认选中一个）+「Sign In」+「Create Account」。没有功能介绍、没有轮播、没有多步问卷。

### 证据来源

- 截图 `overview.jpg`（主界面，四 KPI、Agent Health、CONNECT SESSIONS 列表可见）
- 截图 `welcome.png`（首启：选风格 + 登录/注册）
- 交互指南 `guide-data.js` 中 `overview` 条目的步骤说明：默认页、看四块 KPI、点 agent 跳实时日志
- 截图 `island.png`（桌面上的常驻状态入口）

### 对我们的含义

首屏必须「先回答状态，再提供动作」。但我们的产品与它定位不同：它观察外部 agent，我们要主动分派员工，所以首屏应当是「状态条 + 一句话指令 + 当前编排 + 时间线」，而不是纯仪表盘。

## 2. 导航结构

### 观察结果

**单一左侧栏，按用户意图分成 4 组，共 18 个一级入口；设置沉在最后一组底部；没有顶栏一级导航，没有多级折叠菜单。**

| 分组 | 一级入口（按真实顺序） | 组织逻辑 |
|---|---|---|
| Monitor（监控） | 总览、实时监控、统计、连接 | 我现在花了多少、agent 在干什么、接了谁 |
| Optimize（优化） | 体检、清理、规则 | 哪里浪费、怎么修、长期规则 |
| Secure（安全） | MCP 安全、预警 | 工具面和预算/异常告警 |
| Library（工具箱） | 提示词库、知识图谱、历史、协作、农场、加速、动态壁纸、伙伴、设置 | 可复用资产 + 趣味/皮肤 + 设置 |
| （特殊） | 灵动岛 | 不在侧栏，是浮在所有窗口之上的常驻入口；指南里单独给一栏保证可点 |

页面内部再分标签页，例如实时监控按 agent 分 tab，统计分「小票 / 图表 / 成本」，协作分「Live / Activity / Stats / Inbox」，预警分「Recent / Settings」，历史分「今天 / 周 / 月 / 全部」。**层级只有两层：侧栏一级 → 页内标签，没有第三层菜单。**

侧栏视觉上信息很密：图标 + 名称 + 部分条目带「PRO」角标；设置不是一个独立的大入口，而是工具箱组最后一项，靠近底部用户区。

### 证据来源

- 交互指南 `guide.html` 的 `aside.side` + `nav` 结构；`guide-data.js` 末尾的 `G.GROUPS = ['Monitor','Optimize','Secure','Library']` 与 18 个 feature 的 `group` 字段
- 截图 `overview.jpg` 左侧栏可见 MONITOR / OPTIMIZE / SECURE / LIBRARY 分组
- Windows 页说明「same frontend, same features」，可认为 Windows 与 macOS 导航一致

### 对我们的含义

值得学的是「按用户任务分组，而不是按系统模块分组」；不值得学的是「18 项全部平铺」。我们现有控制台是 19 个一级入口（业务 10 + 治理 8 + 设置 1），问题同源。本次不发起导航重构，但管家主面板必须先承担聚合职责，避免用户为了发一句话而先找入口。

## 3. 核心交互

### 观察结果

**它没有「新建任务 → 填表单 → 等待执行结果」的主链路。核心交互是「接管 → 观察 → 干预 → 看下游变化」。**

- **发起**：发生在产品外部。用户在 Claude Code、Cursor、ChatGPT、VS Code 或任意输入框里正常打字；Terse 在发送前拦截并压缩，或从系统层捕获当前输入框内容后替换。
- **接管**：在「连接」页找到正在用的 agent，点「连接」，角标从灰变 live，下一轮即生效，不需要重启 agent。
- **观察**：实时监控页按 agent 分 tab，逐行显示工具调用（Read、Grep、Bash 等），每行右侧是这一行的 token 增减；统计页按天/模型/项目给出费用。
- **干预**：体检页给出 11 项扫描结果，每条带一键修复；规则页是长期开关；MCP 页关闭用不到的工具；灵动岛在 agent 触碰敏感操作时弹出权限卡。
- **结果呈现**：不是一条「任务完成」消息，而是分散在真实下游：终端里多了一行、配置文件被改、磁盘释放了多少、系统通知弹出、桌面粒子变化。交互指南对每个功能都单独写了「effect（点完之后 app 之外发生了什么）」，这是它最核心的产品表达。
- **会话历史**：有「历史」页，但存的不是聊天记录，而是每一次被观察会话的完整上下文与锚点，可「恢复」继续，避免重新解释任务。
- **任务列表**：没有传统任务列表。最接近的是「已接管会话列表」（按 agent/session 维度）和「体检问题列表」（按影响排序）。
- **运行状态**：有。live 角标、实时 token 流、burn rate、上下文占用百分比、agent 活动流。

### 证据来源

- `guide-data.js` 每个 feature 的 `what / how / effect / demo` 四段结构，尤其 `effect` 字段
- 截图 `overview.jpg`：CONNECT SESSIONS、Agent Health、顶部红色 「Context 100% full — quality is dropping. Run /compact now. [Fix]」横幅
- 截图 `island.png`：常驻 pill + 悬停浮出的 SAVED / CACHE / FOCUS 小卡

### 对我们的含义

它把「结果」做成了可验证的下游事实，而不是一句 toast。我们的管家面板同样要让每一句指令最终落成可追溯的执行记录、产物和审计事件；但我们必须补上它缺的东西：**一个统一时间线**，把分散在各处的执行结果汇总回一条用户能读的线。

## 4. 上手引导

### 观察结果

**公开材料能确认的首启引导只有一屏、一个问题：选风格。**

流程是：打开 → 亮色欢迎页（设备框内是主题色板，默认已选一个）→「Sign In」或「Create Account」。没有步骤指示器、没有「跳过」按钮、没有业务问卷、没有功能介绍轮播。它不问用户用什么模型、不要求 API Key、不要求选择工作场景。

登录后的第一组动作，在指南里被拆成「连接」页三步：找到你在用的 agent → 点「连接」→ 角标变 live 即生效。Windows 说明页写明「30 天免费试用在首次启动时开始」。除此之外，**没有公开证据能证明登录后还有几步问卷或引导**。由于任务禁止安装安装包，这一段的真实完整流程属于「未能获取」，不做推测。

另外，它的「交互指南」本身承担了上手教育：不是文档站，而是一个可点击的 app 复刻，每个功能都按「这是什么 → 怎么用 → 点完后下游发生了什么」讲解。这更像是「上手材料」，不是「首启向导」。

### 证据来源

- 截图 `welcome.png`
- `guide-data.js` 中 `connection` 条目
- `https://terseai.org/for-windows` 的 FAQ：「A 30-day free trial starts on first launch」
- 交互指南页头文案「Click through the real app」

### 未能获取

- 登录后的完整首启流程（是否还有权限引导、订阅引导、连接 agent 的强制步骤）
- 是否有「跳过」机制的真实交互
- 阻塞原因：需要安装客户端并登录，任务明确禁止安装；官网与指南未公开这部分

## 5. 配置入口

### 观察结果

**配置不藏深层菜单，全部是一级入口；没有发现 API Key 配置项。**

| 配置项 | 入口位置 | 层级 |
|---|---|---|
| 账号 / 登录 / 注册 | 首启欢迎页；登录后用户区 | 第 1 层 |
| Agent 接入 | Monitor → 连接 | 第 2 层（侧栏项本身就是页面） |
| MCP 工具管理 | Secure → MCP 安全 | 第 2 层 |
| 预警阈值 / 通知渠道 | Secure → 预警，页内「Settings」标签 | 第 2 层 + 页内 tab |
| 启动行为、默认压缩档、权限处理、语言、数据存放位置 | Library → 设置 | 第 2 层，侧栏最后一组 |
| 压缩模式（轻/标准/激进） | 设置页 / 首页底部全局控制条 | 第 1～2 层 |

没有三级菜单，没有「设置 → 高级 → 开发者 → …」这种路径。设置页的说明也强调「改完即存」，不要求点保存。

**API Key**：官网、指南、价格页、商店页都没有出现用户自填 API Key 的入口；产品卖点是本地优化 + 订阅登录，不是自带密钥。Chrome 扩展明确写「可选登录」，VS Code 扩展写「通过侧边栏登录」。因此「API Key 藏在哪」这一问，在该产品上应回答为「不存在这个入口」，而不是「藏得深」。

### 证据来源

- `guide-data.js` 的 `settings`、`mcp`、`alerts`、`connection` 条目
- 截图 `overview.jpg` 侧栏顺序
- Chrome 商店页「Optional sign-in enables usage sync…」
- VS Code 市场页「Sign in via the Terse sidebar」

### 对我们的含义

我们的模型 Provider、API Key、权限、租户配置比它复杂，不能照搬「只有一个设置页」。但可以照搬它的**入口深度原则**：任何高频配置最多两层到达；「系统设置」固定在侧栏底部；密钥类配置进入设置中的独立分区，并与普通偏好分开。

## 6. 状态与反馈

### 观察结果

它不用「任务卡片 + 进度百分比」表达状态，而是用**指标、健康分、问题计数、角标和下游事实**表达。

| 状态 | 表达形式 | 证据 |
|---|---|---|
| 运行中 | agent 行出现 live 角标；实时日志逐行追加；KPI 数字实时跳动；灵动岛 pill 显示当前 agent 与实时增量 | `overview.jpg`、`island.png`、`guide-data.js` 的 `observe` |
| 成功 | 日志行前出现 ✓；分数从 74 → 96；「fixed / swept / disabled」替换问题值；右侧 effect 显示真实结果 | `guide-data.js` 的 `doctor`、`cleanup`、`rules` |
| 失败 / 风险 | 橙色或红色日志行；顶部红色横幅（上下文 100% 满、质量下降）并带「Fix」；预警越线弹系统通知 | `overview.jpg` 顶部横幅；`alerts` 条目 |
| 部分完成 | 「3 fixed · 6 issues · 1 need attention」这种「已修 / 剩余 / 需注意」三元组；健康分与问题数并存 | `overview.jpg` 的 Agent Health 卡 |
| 等待人决定 | 灵动岛权限卡：仅此一次 / 始终允许 / 拒绝；选「始终」写入规则，下次不再问 | `guide-data.js` 的 `island` |
| 空闲 | agent 行显示 idle；无事件时界面静止，官网明确「never fakes activity」 | `guide-data.js`、官网首页「Calm when you are」 |

反馈的关键不是颜色，而是**因果可见**：每个动作都给前后差值（省了多少 token、释放多少磁盘、分数变化），并说明在 app 之外发生了什么。它很少用纯 toast 作为结果载体。

### 对我们的含义

我们的四态必须比它更明确：`排队中 / 运行中 / 等待审批 / 已完成 / 部分完成 / 失败 / 已中止`。其中「部分完成」必须显示完成数和总数，不能模糊成「基本完成」；「失败」必须保留错误码与重试入口；「已中止」必须标明是人中止还是系统中止。所有状态必须来自后端真实字段，不能用前端计时器或动画推断。

## 7. 视觉基调（只描述规律）

### 观察结果

- **两套场景，一套强调色**：首启是亮色单屏，主应用是深色工作界面；强调色贯穿两处，形成统一品牌感。
- **单一高饱和强调色 + 深中性底**：主界面背景接近黑灰，强调色只用于「当前选中、关键数字、可执行按钮」；状态色（成功/警告/危险/信息）独立于品牌强调色。
- **数字等宽、文字无衬线**：所有金额、token、百分比、分数用等宽字体，便于纵向对齐和快速扫描；正文用无衬线。
- **分组标题小号、全大写、拉开字距**：侧栏分组用极小的标签式标题，和可点击项形成明显层级差。
- **卡片薄边框、低对比面板**：卡片不靠重阴影，而靠 1px 级别的弱边框和比背景略亮的面板色分层；卡片内部紧凑，留白主要放在区块之间。
- **固定节奏的 KPI 行**：首屏固定四块等宽 KPI，形成「扫一眼就知道今天怎样」的节奏；下面才是列表和图表。
- **一个视觉主角**：桌面版把动态粒子壁纸作为背景主角，应用窗口浮在上面；界面本身尽量克制，不与背景抢。
- **圆角中等、开关胶囊化**：卡片与按钮圆角一致；布尔配置统一用胶囊开关，减少「保存」按钮。
- **页内标签代替弹窗**：统计、协作、预警、历史都用页内 tab 切换，不堆叠多层弹窗。

### 证据来源

- 截图 `welcome.png`、`overview.jpg`、`island.png`
- `guide.html` 的结构分层（侧栏 / 主面板 / 右侧解释栏；未复制其样式值）

### 对我们的含义

我们已有自己的设计 token 和浅色/深色体系，不应换成它的荧光深色。可借用的是**节奏规律**：四块 KPI、等宽数字、微标签分组、薄边框卡片、页内 tab、布尔用开关。不要借用具体色值、圆角数值、字体清单或粒子背景。

## 8. Chrome 扩展与 VS Code 的定位差异

### 观察结果

| 形态 | 解决的问题 | 关键交互 | 证据 |
|---|---|---|---|
| macOS / Windows 客户端 | 操作系统级的「管家」：接管本机所有 agent、任意应用输入框捕获、预算熔断、体检、灵动岛、桌面壁纸、宠物 | 全局常驻；点连接接管；灵动岛权限卡；一键修复 | 官网首页、`for-windows`、`guide-data.js` |
| Chrome 扩展 | 浏览器里的 AI 聊天用户：不想装桌面端、也不想离开网页 | 在任意 AI 聊天输入框里捕获 → 优化 → 写回；三档模式；token 计数；技术标签；撤销；可选登录 | Chrome 商店页 |
| VS Code 扩展 | 编辑器内的 agent 用户：所有工作都在 IDE 里完成 | 活动栏侧边面板；自动检测编辑器内 agent；上下文占用条；成本/燃烧率/缓存效率；选中文本右键优化替换；快捷键；可装 Claude Code hooks | VS Code 市场页 |

一句话区别：**Chrome 解决「网页聊天框里的 token 浪费」，VS Code 解决「编辑器内 agent 的可见性与就地优化」，桌面端解决「跨应用、系统级的接管与治理」。** 三者共享同一套优化引擎和账号，但界面形态按用户所在场景裁剪：浏览器里只给「捕获-优化-替换」的最小闭环，IDE 里给「监控面板 + 就地替换」，桌面端才给全量仪表盘和常驻 UI。

### 对我们的含义

我们不需要复制这三种形态，但可以借用这个原则：**同一套能力，按场景裁剪成不同厚度的界面**。Web 控制台是厚界面（治理、审计、编排）；如果未来做 IDE/浏览器触点，只暴露「当前任务、当前员工、当前审批、结果回链」四件事，不把整个控制台塞进去。

## 9. 值得借鉴的 5 条

### 1）首屏先回答状态，再要求动作

- **做法**：第一屏固定「四块真实指标 + 一个健康判断 + 一组正在运行的会话」，让用户在 3 秒内知道系统现在怎样。
- **理由**：它把「我该点哪里」变成「我现在处于什么状态」，降低新用户迷路；也避免首页变成功能目录。
- **落到我们**：管家主面板顶部固定四项真实指标：今日指令数、进行中编排、待你审批、系统健康；每项必须能点进对应页面。

### 2）侧栏按用户任务分组，最多两层

- **做法**：Monitor / Optimize / Secure / Library 四组，页内再用 tab 分区；设置沉底。
- **理由**：用户按「我要干什么」找入口，而不是按「系统有哪些模块」找入口；两层结构让 18 个入口仍可扫描。
- **落到我们**：不改现有 19 项导航，但把管家主面板做成聚合入口；治理类入口保持折叠分组，设置固定在底部。

### 3）每个动作都解释「下游发生了什么」

- **做法**：每个功能固定四段：这是什么、怎么用、点完后 app 之外发生了什么、演示。结果不是 toast，而是终端/文件/通知/桌面上的真实变化。
- **理由**：建立信任，让用户知道系统没有假装工作；也让「撤销/回滚」有依据。
- **落到我们**：时间线每一行都要有「影响」：创建了哪个 Goal、分配给了谁、调用了哪个工具、写了哪条审计、产出哪个文件；执行失败要显示原始错误与可重试入口。

### 4）常驻状态条 + 三选一权限卡

- **做法**：一个始终可见的轻量状态入口，显示当前 agent、实时增量、健康；遇到敏感动作时展开为权限卡，给「仅此一次 / 始终允许 / 拒绝」，选「始终」写入规则。
- **理由**：把审批从「深菜单里的待办」变成「发生这一刻的就地决定」，同时保留长期授权。
- **落到我们**：管家面板顶部保留「管家状态条」；审批以时间线内联卡片呈现，三选一（本次允许 / 始终允许 / 拒绝），「始终允许」必须落到现有审批规则与审计，不能只记在前端。

### 5）用可点击的应用复刻做上手材料

- **做法**：不是写文档，而是做一个可点击的界面复刻，每个功能都能点、状态会变、右侧解释下游影响。
- **理由**：用户在不安装、不登录的情况下就能理解产品；同时减少客服成本。
- **落到我们**：做一个「管家使用指南」页面，用只读 mock 状态复刻管家面板的四个区域，允许点击「发一句话 → 看派工 → 看时间线」，但必须标注「演示数据」，且不与真实控制台混用。

## 10. 不要照搬的 3 条

### 1）18 个一级入口平铺，且把趣味模块和生产模块并列

- **它的问题**：农场、宠物、动态壁纸与「体检、MCP 安全、预警」同属 Library 组；对老用户是乐趣，对新用户是噪音，真正的生产入口被稀释。
- **我们为什么不照搬**：我们的控制台是治理与执行系统，一级导航必须保持任务语义；趣味模块不应与审批、审计同级。
- **替代方案**：生产入口保持一级；实验性/趣味能力放「应用」或独立实验室入口，默认不在首屏出现。

### 2）高饱和单色荧光 + 全屏动态粒子背景

- **它的问题**：视觉辨识度极强，但也把品牌绑死在一个色相上；长时间盯盘容易疲劳，截图和文档里也很难保持可读性。
- **我们为什么不照搬**：我们已有自己的设计 token、浅深色体系和红/橙/绿状态语义；换色会破坏既有页面一致性。
- **替代方案**：只借「单一强调色 + 深中性底 + 等宽数字」的节奏，不使用其色值、粒子背景或动效。

### 3）「无需账号、房间码即凭证」的轻身份模型

- **它的问题**：房间码本身就是凭证，适合开发者协作，但不适合有租户、RBAC、审批、审计链要求的企业控制台。
- **我们为什么不照搬**：我们的每条执行都必须能归因到主体、租户、权限与审计序号；轻身份会直接打穿现有安全模型。
- **替代方案**：保留「低摩擦加入」的体验（邀请链接、扫码进入项目），但身份仍由现有登录与 RBAC 派生，邀请链接只做授权，不做身份。

### 11.3 管家主面板：一句话 → 派工 → 时间线

**信息架构（桌面端 12 栅格）**

```
┌─────────────────────────────────────────────────────────────────────┐
│ 顶栏：管家主面板 · 搜索 · 通知 · 主题 · 用户                        │
├───────────┬─────────────────────────────────────┬───────────────────┤
│ 侧栏      │ 状态条：今日指令 / 进行中编排 /      │ 右栏              │
│ 业务      │         待你审批 / 系统健康           │ 在岗员工（实时）  │
│ ...       ├─────────────────────────────────────┤ 待你决定（审批）  │
│ 治理      │ 指令框：一句话 + 关联项目/知识 + 发送 │ 最近产出          │
│ ...       ├─────────────────────────────────────┤                   │
│ 设置      │ 当前编排卡：Goal / 步骤 / 员工 / 停止 │                   │
│           ├─────────────────────────────────────┤                   │
│           │ 时间线：你 / 管家 / 员工 / 系统       │                   │
│           │        + 内联审批卡 + 汇总卡          │                   │
└───────────┴─────────────────────────────────────┴───────────────────┘
```

**交互链路（全部走现有能力）**

1. 用户在指令框输入一句话，可选关联 `project_id`；发送调用 `createGoal({ natural_language, project_id, background: true })`。
2. 时间线立即插入「指令已接收」行，带 `correlation_id`；状态来自接口返回，不用前端假进度。
3. 管家编排卡展示 Goal 状态与 Planner 产出的步骤；每一步的 `pending / running / done / failed` 来自后端，不能由前端计时器推进。
4. 员工来自 `/v1/dashboard/roster` 与 `/v1/employees`；每张员工卡显示真实状态与当前任务。
5. 执行过程汇总进时间线：员工动作、工具调用、结果、审批请求、审计事件，按 `goal_id` / `correlation_id` 归并。
6. 结束后在时间线顶部生成一张「管家汇报」卡：结论一句话、完成/部分完成/失败、产物链接、耗时、审计序号、知识与记忆引用，以及「继续 / 重试 / 归档」。
7. 审批卡三选一：本次允许 / 始终允许 / 拒绝；「始终允许」写入现有审批规则并产生审计事件，不在前端自建规则。
8. 停止/重规划直接复用 `stopGoal` / `replanGoal`；按钮只在 Goal 真实处于 running 时可用。

**时间线行字段（建议契约）**

| 字段 | 用途 |
|---|---|
| `id` / `timestamp` | 排序与去重 |
| `actor_type` | human / butler / employee / system |
| `actor_name` | 你、管家、员工名、系统 |
| `event_type` | 指令、规划、派工、工具调用、审批、结果、审计、异常 |
| `status` | queued / running / waiting_approval / completed / partial / failed / aborted |
| `title` / `detail` | 一行摘要 + 展开详情 |
| `goal_id` / `task_id` / `execution_id` | 下钻到目标与执行 |
| `correlation_id` | 把同一次指令的所有事件串成一条线 |
| `audit_seq` | 一键跳到审计链 |
| `artifacts` | 文件、报告、知识条目 |

**归并规则**：只按后端真实存在的关联字段归并；字段缺失的行显示「未关联」，不允许为了好看把不同 Goal 的事件拼在一起。

### 11.4 三种形态的差异

- **桌面端**：完整三栏；状态条 + 指令框 + 编排卡 + 时间线 + 右栏。
- **网页紧凑态**：右栏折叠到时间线下方；状态条保持四项。
- **手机端**：沿用现有底部导航四项；指令框吸底，时间线全宽；右栏内容拆成时间线上方的两个横向卡片；审批卡置顶，保证「待你决定」不被淹没。

### 11.5 明确不做

- 不新增一级导航、不删除现有页面、不重写路由。
- 不引入桌面宠物、壁纸、农场等趣味模块。
- 不使用粒子背景、荧光单色主题或它的任何资源。
- 不在后端新增「为了时间线好看」的假事件；缺字段就如实显示未关联。
- 不把审批规则存在前端；始终允许必须落到后端策略与审计。

## 12. 我们的首屏应该长什么样（可直接交付实现）

### 12.1 默认首屏（无进行中编排）

从上到下、从左到右：

1. **顶栏**：左侧标题「管家主面板」；中间全局搜索；右侧通知、主题切换、用户头像。保持现有 `Shell` 顶栏，不新增控件。
2. **状态条**：四块等宽指标卡，横排：
   - 今日指令数（来自真实指令/Goal 计数）
   - 进行中编排（Goal 处于 running/planning 的数量）
   - 待你审批（审批中心真实待办数）
   - 系统健康（`/v1/ready` 的真实比例；证据链异常时显示警告文案）
   - 每块卡右下角给一个可点击的「查看」入口，跳到对应页面。
   - 任一接口失败时显示「—」+「无法读取」，不显示 0，不编造。
3. **指令框**（首屏最重要的动作）：
   - 单行/两行自适应输入，占位文案用我们自己的业务语言，例如「告诉管家你要做什么，例如：把本周客户反馈整理成一份可执行计划」。
   - 左侧「关联」按钮：选择项目（现有 Projects）、可选知识范围；右侧「发送」。
   - 下方三个快捷意图 chips，用真实业务场景（如「整理本周反馈」「生成周报」「检查项目风险」），点击只填入输入框，不直接执行。
   - 键盘 Enter 发送，Shift+Enter 换行；发送后输入框清空，焦点保留。
4. **空态编排卡**：不画假进度。内容为三行解释：
   - 「你说一句话 → 管家拆成步骤 → 分派给在岗员工 → 结果汇总回时间线」
   - 右侧一个「查看在岗员工」链接，跳到「我AI员工」。
5. **空态时间线**：显示三到四条示例行，但必须标明「示例」，或者干脆只显示一句「时间线会记录：指令、派工、执行、审批、结果」。不要填入假时间、假员工名。
6. **右栏**：
   - 在岗员工：来自 roster，显示姓名、状态点、当前任务；最多 5 行 + 「全部」。
   - 待你决定：审批待办，最多 3 条，每条「谁 / 要做什么 / 风险」+ 一个跳转。
   - 最近产出：来自工作区文件/结果，最多 3 条。

### 12.2 提交一句话之后

按真实时序更新，不预先填满：

1. 时间线插入「你 · 指令已接收」，显示 correlation id 的短码。
2. 编排卡从空态切为「规划中」，显示 Goal 标题与状态；若 Planner 尚未返回，显示骨架，不显示假步骤。
3. 步骤逐条出现，状态只随接口变化；当前步骤高亮，已完成步骤显示产物链接。
4. 员工卡出现「正在执行」标记，来自真实员工状态。
5. 遇到审批：时间线内联插入审批卡，显示「要做什么 / 为什么 / 影响范围」，三个按钮；未处理时该行保持 `waiting_approval`，编排卡同步显示「等待你决定」。
6. 结束：
   - 已完成：顶部「管家汇报」卡，绿色完成标记 + 一句话结论 + 产物 + 耗时 + 审计链接。
   - 部分完成：琥珀色标记 + 「完成 3 / 共 5」+ 失败步骤列表 + 「重试失败步骤」。
   - 失败：红色标记 + 错误码 + 原始错误摘要 + 「重试 / 中止」。
   - 已中止：灰色标记 + 「由你中止」或「由系统中止」+ 时间。
7. 汇总卡固定在时间线顶部（不是滚动到底才看见），保证用户回到页面第一眼看到结果。

### 12.3 视觉与状态规则

- 沿用现有设计 token；不引入竞品色值。
- 数字统一等宽；状态色只用于状态，不用于装饰。
- 动效只表达真实状态变化：新行进入、状态翻转、汇总卡出现；不做循环呼吸灯来假装「AI 正在思考」。
- 所有异步区域有骨架、空态、错误态、重试；禁止把错误吞成空列表。
- 审批卡必须带「谁、做什么、为什么、影响范围」，不能只有一句「允许？」。

### 12.4 验收清单（实现方自检）

1. 首屏默认落在 `overview`，不新增导航项。
2. 四块状态指标全部来自真实 API；断网/503 时显示「无法读取」，无 0、无假数。
3. 一句话能创建后台 Goal，并返回可追踪的 id；停止按钮只在 running 时可用且真的能停。
4. 时间线只展示后端存在的事件；关联缺失显示「未关联」。
5. 已完成/部分完成/失败/已中止四态可区分；部分完成显示完成数与总数。
6. 审批三选一可用；「始终允许」写入后端规则并产生审计。
7. 右栏员工、审批、产出均有真实空态；不出现假姓名、假任务。
8. 手机端 375 宽度可用，指令框吸底，审批不被遮挡。
9. 页面无循环动画伪造运行状态；所有「运行中」都有真实状态字段支撑。
