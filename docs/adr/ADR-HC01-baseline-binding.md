`HC-01-Baseline-Reconciliation-Decision-Package.md`（§0 immutable 实测、§9–§12），

### 1.1 保管断裂（必须随本 ADR 一起披露）

快照在**取证之后**被一个**未查明身份的进程**以读写方式打开：`-wal` / `-shm`
的 mtime 晚于取证时刻。可证的事实是：

* 主文件字节数、`page_count`、freelist 未变；
* `-wal` 为 0 字节；
* `PRAGMA integrity_check` 为 `ok`；
* 内容完整性（137 个重复 seq / 169 条冗余行）与取证记录逐项吻合。

不可证的事实是：**谁打开过它、打开期间做了什么**。行为主体**未查明**，也不能靠
现有日志归因。因此：

> **本 ADR 与所有引用该快照的文档，一律写作「保管链断裂、行为人未查明」；
> 不得表述为「快照未被访问」或「保管完好」。**内容完整 ≠ 保管完好。

### 1.2 C11 的 BLOCKED 与「已裁决」的关系

`scripts/verify_readiness.py::check_hc01` 对 HC-01 恒返回 `BLOCKED`，因为它把 HC-01
当作**冻结的人类主权门**，而不是一个可由工程自行改判的检查项。本 ADR 记录 owner 的
5 项裁决后，两套口径并存且互不矛盾：

* **机器口径不变**：`check_hc01` 仍打印 `BLOCKED`，这是门禁设计（Decision Isolation），
  **不是**「工程侧还有活没干完」「测试没过」「构建坏了」，也不该为了好看去改；
* **人端口径已收口**：HC-01 的 5 项裁决已由 owner 拍定并记录在本 ADR；台账、交付清单与
  证据中 C11 的状态改为「**已裁决（ADR-HC01）**」，不再写「待人工裁决 / HUMAN DECISION PENDING」；
* 因此 `RELEASE READY=False` 的理由**只剩 C9**（桌面分发形态无真实 CD，见

## 2. Decision（5 项，全部按 owner 裁决落地）

### 2.1 Baseline binding → **Path A：以 live 为迁移源**

* **裁决**：迁移源绑定**现网 live**（`schema_version=9`、331,611 行、基线之后 558 行
  干净追加）；旧快照仅作**历史证据**保留，不参与迁移。
* **理由**：live 是唯一 schema-current 且含真实追加尾的对象；分叉区与快照逐行相同
  （`dup_sets_identical=true`），走 A 不丢任何取证信息。
* **落地约束**：live 有 WAL 在写，迁移前必须**静默 / checkpoint 取一致切面**；
  迁移开始时现场记录 live hash / 行数 / `schema_version` / `max(seq)`（见 2.3 参数化）。
* **可推翻条件（须新 ADR 覆盖，工程侧不得自行切换）**：
  1. live 在迁移前出现不可解释的结构性损坏（`PRAGMA integrity_check` 非 `ok`，或主文件字节 /
     `page_count` 与本次记录不符），而旧快照内容完整性仍成立；
  2. live 的追加尾被证明**不干净**（存在快照之外、且无法归因的写入）；
  3. live 因业务无法停写 / 静默，取不到一致切面，而旧快照可证明此后无新增内容。

### 2.2 Custody disposition → **接受并披露（accept-with-disclosure）**

* **裁决**：接受该快照作为历史证据，**但任何引用都必须写明「保管链断裂、行为人未查明」**。
* **理由**：主文件自取证后未变、`-wal` 0 字节、`integrity_check=ok`，内容完整性有证；
  缺的只是操作者归因，不是内容。
* **落地约束**：今后冻结基线一律**只读 ACL + 一次性位置 + 记录 operator + 采集前后
  hash**，防同类断裂再次发生。清单与证据页必须一眼可见这条披露。
* **可推翻条件**：
  1. 出现可归因的新证据证明行为人身份或访问目的，足以改写结论；
  2. 快照主文件 hash 发生变化，或 `integrity_check` 不再为 `ok`，内容完整性被推翻。
  两种情形都应改为「隔离替换」或「标 UNRESOLVED」，并以新 ADR 覆盖本条。

### 2.3 固定 / 参数化拆分

* **固定（历史事实，不可篡改）**：137 个重复 seq、169 条冗余行、`UNVERIFIED` / RCA-1
  结论、取证时刻 `2026-09-24T21:27:34Z`、`d6b2fea…`（取证时源锚）、`b6e27d…`（快照件
  身份）、基线 `total_rows=331,053`。
* **参数化（运行时读）**：live 的 hash / 行数 / `schema_version` / `max(seq)`。
* **理由**：I1 现在把 `331,053` / `d6b2fea` 同时当历史基线与 live 期望，而 live 已到
  `331,611` / `a4a347…`；不拆分就会长期**假红**，并诱导有人去改阈值。
* **可推翻条件**：新证据表明 137 个重复 seq / 169 条冗余行的取证事实本身有误，或 live 的
  seq 语义发生不可逆变化，使「固定历史 + 参数化 live」不再成立；此时须新 ADR 并同步修订
  I1–I10 的固定清单。

### 2.4 Schema reconciliation → **不做 v1→v9 迁移**

* **裁决**：不做。与 2.1 一致：只有「从快照迁移」才需要 v1→v9；Path A 不需要。
* **落地约束**：文档里必须写明「旧快照是 v1 历史件，不参与迁移」，避免后人误开迁移路径。
* **可推翻条件**：仅当 2.1 被推翻并改绑旧快照（Path B / C）时，v1→v9 迁移才重新成为必选；
  本条随 2.1 联动失效。

### 2.5 Re-capture authorization → **暂不重采；条件写死**

* **裁决**：**推迟**，不现在授权新采基线；授权条件是 **F1–F6**（单写者租约 /
  `BEGIN IMMEDIATE` / `UNIQUE(seq)` / `busy_timeout` / 围栏）上线并跑过 soak。
* **理由**：在 F1–F6 上线前重采，只是把分叉期再复制一份；A 路径的迁移起始清单在迁移时
  现场记录即可。
* **落地约束**：重采时必须按 §6 保管控制执行（只读 ACL / 一次性位置 / 记录 operator /
  前后 hash）。
* **可推翻条件**：
  1. **F1–F6 全部上线并通过 soak** —— 这是写死的授权前置条件，满足后由 owner 重新开题评估，
     **不自动授权**；
  2. live 在 F1–F6 完成前发生损坏且旧快照不可用，必须紧急重采 —— 由 owner 紧急授权，
     事后补新 ADR。

## 3. Consequences

**正面**

* 迁移只有一条路径（live），没有 v1→v9 的高风险迁移分支；
* 历史事实被固定，不会被「为了让校验变绿」而改写；
* live 目标参数化，消除 I1 的长期假红；
* 保管断裂以既定措辞随 ADR 与清单披露，不埋没在证据文件深处。

**代价 / 风险（如实记录）**

* live 是运行中的库，取一致切面需要静默或 checkpoint，迁移窗口有操作成本；
* 旧快照仍是 `schema_version=1`，任何「从快照重放」的旧脚本都不可用；
* 重采延后意味着可审计的新基线在 F1–F6 完成前不存在；
* **机器门 `check_hc01` 仍打印 `BLOCKED`**（冻结的人类主权门设计，未改口径）；人类裁决
  已收口，`RELEASE READY=False` 的理由**只剩 C9**（桌面分发形态无真实 CD，属形态差异，
  不是产品缺陷）。本 ADR 不重跑全量、不改变 `72fd9b17` 的交付凭证口径。

## 4. Compliance / 引用规则

1. 引用旧快照时，必须同时出现「**保管链断裂、行为人未查明**」。
2. 不得把 C11 的 `BLOCKED` 描述成工程缺陷、测试失败或构建失败。
3. 不得为了门禁好看去调 C7 / C11 的阈值或判定口径。
4. 本 ADR 记录后，HC-01 的 5 项裁决即为**已裁决**；后续变更需新 ADR 覆盖。
5. 推翻本 ADR 任何一项，必须以**新 ADR**覆盖本 ADR，并同步更新台账 / 交付清单 / 证据；
   工程侧不得自行改判，更不得为了门禁变绿去调阈值或口径。
