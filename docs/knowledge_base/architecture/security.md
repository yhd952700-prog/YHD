# 安全架构

安全是 LiuHao AI OS 的核心设计原则之一。系统采用纵深防御策略，在内核级别实施多层安全防护，确保人类主权、数据安全和系统完整性。

---

## 安全模型

### 设计原则

LiuHao AI OS 的安全架构基于以下核心原则：

1. **人类主权（Human Sovereignty）**：人类拥有最终决策权，AI 的所有行动都在人类授权下进行
2. **零信任（Zero Trust）**：永不信任，始终验证
3. **最小权限（Least Privilege）**：每个实体只拥有完成任务所需的最小权限
4. **纵深防御（Defense in Depth）**：多层防护，一层失效不影响整体安全
5. **默认安全（Secure by Default）**：默认配置就是最安全的配置
6. **可审计性（Auditability）**：所有操作都有不可篡改的审计记录


## 认证与授权

### 身份认证

#### 支持的认证方式

| 认证方式 | 说明 | 适用场景 |
|---------|------|---------|
| API Key | 静态密钥认证 | 服务端集成、脚本自动化 |
| JWT Token | 基于令牌的认证 | Web 应用、移动端 |
| 用户名/密码 | 传统认证 | 本地部署、初始设置 |
| OAuth 2.0 | 第三方登录 | 企业集成、SaaS 部署 |
| mTLS | 双向 TLS 认证 | 高安全要求的服务间通信 |

#### 身份内核

所有认证请求都经过 Identity Kernel 处理：

```python
# 认证流程
1. 请求携带认证凭证到达网关
2. Security Kernel 拦截并验证凭证
3. Identity Kernel 查找身份并加载权限
4. 生成安全上下文（包含身份、角色、作用域）
5. 请求继续处理，安全上下文贯穿整个请求链路
```

### 授权模型

LiuHao AI OS 采用 **RBAC + ABAC** 混合授权模型。

#### RBAC（基于角色的访问控制）

通过角色分配权限，简化权限管理：

```
用户 → 角色 → 权限
   └──→ 角色 ──┘
```

**内置角色**：

| 角色 | 说明 | 典型权限 |
|------|------|---------|
| `admin` | 系统管理员 | 全部权限 |
| `manager` | 管理者 | 智能体管理、用户管理 |
| `user` | 普通用户 | 使用智能体、管理自己的数据 |
| `viewer` | 观察者 | 只读权限 |
| `agent` | 智能体 | 执行任务、使用工具 |

#### ABAC（基于属性的访问控制）

基于属性进行更细粒度的访问控制：

```
允许 = if (主体属性 匹配 资源属性 匹配 环境属性 满足 策略)
```

**属性类型**：

- **主体属性**：用户角色、部门、安全级别、地理位置
- **资源属性**：数据分类、所有者、创建时间、作用域级别
- **环境属性**：时间、IP 地址、设备状态、风险等级

#### 策略引擎

Policy Kernel 负责策略评估：

```yaml
# 策略示例
policy:
  id: "sensitive_data_access"
  description: "敏感数据访问需要审批"
  effect: "require_approval"
  conditions:
    - attribute: "resource.scope"
      operator: "gte"
      value: "L4"
    - attribute: "subject.role"
      operator: "not_in"
      value: ["admin", "security_officer"]
  approval:
    required: true
    approvers: ["manager", "data_owner"]
    timeout: "24h"
```

### 作用域系统（L0-L7）

数据按敏感程度分为 8 个作用域级别：

| 级别 | 名称 | 说明 | 默认访问角色 |
|------|------|------|-------------|
| L0 | Public | 公开信息 | 所有人 |
| L1 | Internal | 内部信息 | 所有认证用户 |
| L2 | Confidential | 机密 | 授权用户 |
| L3 | Secret | 秘密 | 严格授权 |
| L4 | Top Secret | 绝密 | 极少人 |
| L5 | Restricted | 受限 | 特定人员 |
| L6 | Highly Restricted | 高度受限 | 极少数人 |
| L7 | Sovereign | 最高主权 | 仅人类主权者 |

**作用域过滤原则**：
- 每个请求携带身份的作用域级别
- 所有数据查询自动过滤掉超出级别的数据
- 内核级别强制过滤，应用层无法绕过

## 数据加密

### 传输加密

- **TLS 1.3**：所有外部通信强制使用 TLS 1.3
- **mTLS**：服务间通信支持双向 TLS
- **证书管理**：自动证书轮换和续期
- **HSTS**：HTTP 严格传输安全

### 存储加密

#### 静态数据加密

| 数据类型 | 加密方式 | 密钥管理 |
|---------|---------|---------|
| 数据库 | AES-256-GCM | Vault Transit Engine |
| 文件存储 | AES-256-CBC | 密钥管理服务 |
| 记忆数据 | AES-256-GCM | 每用户独立密钥 |
| 配置文件 | 环境变量加密 | 操作系统密钥链 |

#### 密钥管理

- 使用 HashiCorp Vault 或内置密钥管理
- 密钥定期轮换（默认 90 天）
- 支持 BYOK（Bring Your Own Key）
- 密钥访问审计

### 数据脱敏

敏感数据在输出时自动脱敏：

```
原始数据：
  姓名：张三
  手机号：13800138000
  身份证：110101199001011234

脱敏后：
  姓名：张*
  手机号：138****8000
  身份证：1101**********1234
```

## 审计追踪

### 审计链（Audit Chain）

LiuHao AI OS 使用哈希链（hash-chain）确保审计记录的不可篡改性。

#### 链结构

```
Genesis Block
  ↓
Block #1 ──hash──→ Block #2 ──hash──→ Block #3 ── ...
  ↑                 ↑                 ↑
prev_hash         prev_hash         prev_hash
```

每个区块包含：
- 前一个区块的哈希（`prev_hash`）
- 审计事件数据
- 时间戳
- 当前区块哈希

#### 防篡改原理

- 任何区块的数据改动都会导致该区块哈希变化
- 哈希变化会导致后续所有区块的 `prev_hash` 不匹配
- 因此，篡改任何一条记录都需要重算整条链

### 审计事件类型

| 类别 | 事件 | 级别 |
|------|------|------|
| 认证 | 登录成功/失败、登出、token 刷新 | HIGH |
| 授权 | 权限检查通过/拒绝、策略变更 | HIGH |
| 数据 | 数据访问、修改、删除、导出 | MEDIUM |
| 智能体 | 创建、删除、配置变更 | MEDIUM |
| 工具调用 | 工具执行、参数、结果摘要 | MEDIUM |
| 安全 | 安全告警、威胁检测、策略违反 | CRITICAL |
| 系统 | 配置变更、启动/关闭、更新 | MEDIUM |

### 审计查询

```python
# 按实体查询
audit_logs = client.audit.query(entity_id="user-abc123", limit=100)

# 按时间范围查询
audit_logs = client.audit.query(
    start_time="2026-10-01T00:00:00Z",
    end_time="2026-10-07T23:59:59Z",
    event_type="authentication"
)

# 按操作类型查询
audit_logs = client.audit.query(action="delete", resource_type="agent")

# 验证审计链完整性
result = client.audit.verify_integrity()
print(f"链完整性: {result.valid}")
print(f"已验证区块数: {result.verified_blocks}")
```

## 合规框架

LiuHao AI OS 的安全设计参考以下合规框架：

### 支持的合规标准

| 标准 | 说明 | 状态 |
|------|------|------|
| **GDPR** | 欧盟通用数据保护条例 | 设计对齐 |
| **SOC 2 Type II** | 服务组织控制报告 | 设计对齐 |
| **ISO 27001** | 信息安全管理体系 | 设计对齐 |
| **等保 2.0** | 中国网络安全等级保护 | 设计对齐 |
| **HIPAA** | 美国健康保险流通与责任法案 | 可选配置 |
| **PCI DSS** | 支付卡行业数据安全标准 | 不适用（不处理支付卡） |

### GDPR 合规特性

- **数据主体权利**：支持访问、更正、删除、导出个人数据
- **数据最小化**：只收集必要的最少数据
- **同意管理**：明确的用户同意机制
- **数据处理记录**：完整的数据处理活动记录
- **DPIA**：数据保护影响评估工具
- **数据泄露通知**：72 小时内通知机制

### 数据驻留

- 支持指定数据存储区域
- 数据不跨境传输（可配置）
- 本地部署模式数据完全留在本地

## 智能体安全

### 工具安全

#### 工具执行沙箱

- 危险工具在隔离沙箱中执行
- 文件系统隔离（只能访问指定目录）
- 网络访问控制（白名单/黑名单）
- 资源限制（CPU、内存、执行时间）
- 操作前模拟验证

#### 工具审批机制

```python
# 需要人类审批的工具
approval_required_tools = [
    "shell_exec",        # Shell 命令执行
    "file_write",        # 文件写入
    "file_delete",       # 文件删除
    "api_call_external", # 外部 API 调用
    "email_send",        # 发送邮件
]

# 审批流程
1. 智能体请求调用工具
2. 检查是否需要审批
3. 如需审批，创建审批请求
4. 通知审批人
5. 审批通过才执行
6. 审批结果记录到审计链
```

### 输出安全

#### 内容过滤

- 敏感信息检测和过滤
- 不当内容检测
- PII（个人可识别信息）脱敏
- 输出格式验证

#### 提示注入防护

- 系统提示词与用户输入隔离
- 提示注入检测
- 输出验证（确保输出是智能体的回复，不是被注入的内容）

### 记忆安全

- 每个智能体的记忆相互隔离
- 记忆数据加密存储
- 记忆访问经过作用域检查
- 记忆操作全部审计记录

## 安全最佳实践

### 部署安全

1. **使用 HTTPS**：生产环境必须启用 TLS
2. **网络隔离**：将服务部署在内部网络，通过反向代理对外
3. **防火墙**：只开放必要的端口
4. **定期更新**：及时更新系统和依赖，修复安全漏洞
5. **备份加密**：备份数据必须加密存储

### 配置安全

1. **强密码策略**：使用强密码，定期更换
2. **最小权限**：每个账号只授予必要的权限
3. **禁用默认账号**：生产环境禁用默认管理员账号
4. **API Key 管理**：定期轮换 API Key，不要硬编码
5. **日志脱敏**：日志中不记录敏感信息

### 操作安全

1. **审计日志监控**：定期检查审计日志，发现异常行为
2. **安全告警**：配置安全事件告警
3. **定期审计**：定期进行安全审计和渗透测试
4. **应急响应**：制定安全事件应急响应计划
5. **人员培训**：对操作人员进行安全培训

### 智能体安全

1. **限制工具权限**：只给智能体必要的工具
2. **关键操作审批**：高风险操作必须人类审批
3. **资源限制**：设置合理的资源配额
4. **输出审核**：重要输出经过人工审核
5. **行为监控**：监控智能体行为，发现异常及时干预

## 安全开发流程

### 安全开发生命周期（SDL）

1. **需求阶段**：安全需求分析、威胁建模
2. **设计阶段**：安全设计评审、架构风险评估
3. **开发阶段**：安全编码规范、静态代码扫描
4. **测试阶段**：安全测试、渗透测试、漏洞扫描
5. **发布阶段**：安全评审、发布前检查
6. **运维阶段**：安全监控、漏洞管理、定期审计

- **静态分析**：Semgrep、Bandit
- **依赖扫描**：pip-audit、Safety
- **容器扫描**：Trivy
- **动态测试**：OWASP ZAP
- **代码审计**：人工审计 + 自动化工具
